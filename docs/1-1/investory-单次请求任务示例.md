# Investory 第 1-1 课：单次请求任务示例

## 背景

通用课程里常用的例子是：

- 整理纪要并生成待办
- 根据制度回答问题

这两个例子的共同点是：用户一次性给出明确材料和明确目标，系统在一次请求内完成理解、整理和结构化输出。

对应到 `Investory` 项目里，不建议直接使用“会议纪要”或“制度问答”作为核心例子，因为它们不符合投资理财学习助手的业务语境。

更合适的单次请求任务应该围绕：

- 投资理财知识理解
- 财经材料摘要
- 学习待办生成
- 风险认知提醒

## 对应到 Investory 的任务

### 任务一：整理财经学习材料并生成学习待办

这个任务对应通用例子里的“整理纪要并生成待办”。

在 `Investory` 中，可以定义为：

```text
finance_article_summary
```

或：

```text
learning_material_summary
```

用户请求示例：

```text
请帮我总结这篇 ETF 入门文章，并列出我接下来应该学习的事项。
```

系统需要完成的事情：

1. 理解输入材料的主题。
2. 提炼核心观点。
3. 解释关键概念。
4. 标出可能的风险或误区。
5. 生成后续学习待办。

建议输出结构：

```text
- 核心摘要
- 关键概念
- 重要结论
- 风险提醒
- 后续学习待办
- 信息不足或不确定性说明
```

这个任务属于 `summary` 类任务。

### 任务二：根据投资理财资料回答问题

这个任务对应通用例子里的“根据制度回答问题”。

在 `Investory` 中，可以定义为：

```text
finance_qa
```

或：

```text
concept_qa
```

用户请求示例：

```text
根据这段基金说明，解释一下最大回撤是什么意思？它为什么重要？
```

系统需要完成的事情：

1. 识别用户真正想问的投资理财概念。
2. 只根据用户提供的材料和通用金融常识作答。
3. 用适合学习者理解的方式解释概念。
4. 明确说明依据。
5. 避免变成具体投资建议。

建议输出结构：

```text
- 简明回答
- 概念解释
- 材料依据
- 常见误区
- 风险提示
- 不确定性说明
```

这个任务属于 `qa` 类任务。

## 为什么单次请求适合解决这种问题

单次请求适合 `Investory` 当前阶段，是因为这类任务有几个明显特征。

### 1. 输入边界清楚

用户通常会一次性提供一段文章、基金说明、课程材料或一个明确问题。

例如：

```text
这是我看到的一段基金介绍，请帮我总结重点。
```

或者：

```text
请解释什么是 ETF 跟踪误差。
```

这类任务不需要系统先进行复杂的多轮规划，也不需要持续追踪用户长期状态。只要当前输入足够完整，模型就可以直接完成任务。

### 2. 目标明确

单次请求任务通常只有一个清晰目标：

- 总结一段材料
- 解释一个概念
- 提炼风险点
- 生成学习待办
- 给出一份学习计划草稿

这些目标可以在一次模型调用中完成，不需要拆成多个 agent 或复杂 workflow。

### 3. 输出可以结构化

`Investory` 的第一版任务非常适合结构化输出。

例如财经材料摘要可以固定输出：

```text
summary
key_concepts
risks
todos
uncertainty
```

概念问答可以固定输出：

```text
answer
evidence
misunderstandings
risk_notice
uncertainty
```

结构化输出的好处是：

- 方便前端展示
- 方便写测试
- 方便做 eval
- 方便后续接入日志和学习记录

### 4. 风险边界容易控制

投资理财类产品最重要的问题不是“能不能回答”，而是“回答是否越界”。

单次请求的输入和输出都比较集中，比较容易加入统一规则：

- 只做学习解释，不做投资建议。
- 不直接回答“买什么、什么时候买、买多少”。
- 对数据来源和时间保持谨慎。
- 信息不足时明确说明不确定性。
- 把用户的决策型问题改写为学习型分析框架。

这比一开始做复杂 agent 更容易建立安全基线。

### 5. 工程实现简单，适合作为 MVP

在当前阶段，`Investory` 不需要一开始就做完整 agent 系统。

更合适的实现方式是：

```text
用户请求
-> 任务分类
-> 加载对应 prompt
-> 调用模型
-> 返回结构化结果
```

这正好对应最小任务执行器的设计：

```text
TaskSpec
-> Prompt Loader
-> RequestRunner
-> Structured Result
```

先把单次请求跑通，可以更快验证：

- 任务边界是否合理
- prompt 是否稳定
- 输出结构是否好用
- 风险提示是否足够
- 后续是否值得接入工具或状态层

## 推荐作为第一版 Demo 的任务

第一版最推荐展示这个任务：

```text
财经材料摘要 + 学习待办生成
```

完整流程可以写成：

```text
输入一篇财经文章或基金介绍材料
-> 系统识别为 summary 任务
-> 生成结构化学习笔记
-> 提取关键概念和风险点
-> 生成后续学习待办
```

这个任务比“会议纪要”更符合 `Investory` 的项目定位，也能自然连接后续模块：

- `qa`：继续追问某个概念
- `summary`：总结更多材料
- `study_plan`：把待办扩展成学习计划
- `memory`：记录用户学过什么
- `eval`：检查是否事实错误或越界成投资建议

## 一句话结论

在 `Investory` 中，“单次请求完成任务”的最佳示例不是会议纪要或制度问答，而是“财经材料摘要并生成学习待办”以及“根据投资理财资料回答概念问题”。这类任务输入边界清楚、目标明确、输出可结构化、风险可控，非常适合作为最小任务执行器和第一版 MVP 的起点。
