## 🎯 真正贴合你业务的三个借鉴点

### 借鉴① 统一能力台账(课程模块一,改造而非新建)

**现状问题**:
- `TASKS` 字典有 9 个任务,但**只包含** name/prompt/models
- `side_effect_level` 治理元数据**完全缺失** — 无法区分「纯查询」vs「触发人工审批」
- 没有「风险评估结果需要人工接入」这个隐含逻辑的显式声明

**业务现实**:
- 你的 risk_assessment → 产出 `approval_status=PENDING_HUMAN_APPROVAL` → 触发人工审批
- 其他 8 个任务都是纯读写,不影响 approval gate

**课程对标**:
- risk_assessment = `side_effect_level="write"`(有副作用,需要审批/审计/灰度控制)
- 其余 8 个 = `side_effect_level="read"`(纯产出,可直接展示)

**改造方向**:
```python
# task_spec.py — 加三个字段(向后兼容,有默认值)
@dataclass(slots=True)
class TaskSpec:
    name: str
    prompt_name: str
    input_model: type[BaseModel]
    output_model: type[BaseModel]
    side_effect_level: str = "read"  # read / write / exec
    tag: str = ""                    # learning / document_review / risk
    desc: str = ""                   # 供治理端查看
```

**元数据分配**(业务上已有,只需显式化):
- `side_effect_level="write"`:INVESTMENT_DOCUMENT_RISK_ASSESSMENT_TASK
- `side_effect_level="read"`:其余 8 个
- `tag="learning"`:qa、summary、brief
- `tag="document_review"`:extract、analyze、synthesize、plan、single_pass
- `tag="risk"`:risk_assessment、reflection

**收益**:
- 风险审批、审计、灰度都能统一依赖这一个维度,而不是散落在 flow 代码里
- `routing.py` 可加 `list_specs_by_tag(tag)` 和 `list_specs_by_side_effect(level)` 查询
- 为未来「多租户/角色权限控制」奠基

**现状证据**:
在 `document_review_flow.py` 里,**已经同时支持两种规划策略**:

```python
# 策略一:规则驱动(chunk review)
def _build_chunk_review_todo_plan(self, state):
    # 确定性生成 extract + analyze + synthesize 三层 DAG
    # 不调 LLM,完全由规则(chunk 数量、focus 字段)驱动

# 策略二:模型驱动(LLM plan)
def generate_review_todo_plan(self, state):
    if should_use_chunk_review(state):
        return self._build_chunk_review_todo_plan(state)
    else:
        # 调 INVESTMENT_DOCUMENT_REVIEW_PLAN_TASK(LLM 生成 plan)

```

只差**从 `if` 写死抽出接口**。

**业务上的 plan 变体**(你已有,只需识别):

| 版本 | Plan 策略 | 当前写法 | 用途 |
|------|---------|--------|------|
| v0(baseline) | 模型驱动 | `INVESTMENT_DOCUMENT_REVIEW_PLAN_TASK` | 第一版,让 LLM 自主规划 |
| v1(并发优化) | 模型驱动 + todo DAG 并发 | 同 v0,但 `TodoExecutionRunner` 会并发执行 | 加快执行速度 |
| v2(风险审批) | 规则驱动 chunk review | `_build_chunk_review_todo_plan` | 降低成本,确定性处理,通过审批 |
| v3(反思优化) | 模型驱动 + 反思门 | 同 v1,但加上 `reflect_review_output` | 提高质量 |
| 灰度/测试 | 固定规则(mock plan) | 新增 `FixedAuditPlanHandler` | A/B 测试不同规划逻辑 |

```python

        self,

        llm_router: ... | None = None,

        ...

        self.plan_handler = plan_handler or self._default_plan_handler()
    
    def _default_plan_handler(self) -> ReviewPlanHandler:
        """保持现有行为:根据 should_use_chunk_review 二选一"""
        # 返回一个包装 if 逻辑的 handler
```

**收益**:
- v1/v2/v3 演进本质就是 plan 策略的演进,不用改图骨架
- 灰度/测试可轻易切 handler,而不是改 flow 代码
- 为「不同场景(高成本vs低成本、高精度vs快速反馈)」提供同一套接口

### 借鉴③ 可替换 Execution Handler(课程模块四,成本最低收益最高)

**现状**:
- `TaskExecutor` **已经在 flow 构造函数支持依赖注入**
- 测试中你必须**打真实 LLM 调用**(慢、贵、不稳定)
- 这是 `test-results/` 目录里为什么有 concurrency fix、retry、timeout 等工作日志的根本原因

**业务需求识别**:
投资文档审查流程有多套测试场景,但全都依赖真实 LLM:
- flow 节点逻辑测试(各个分支是否正确路由?)
- todo 并发逻辑测试(依赖是否正确计算?)
- 反思门测试(criteria 是否生效?)

目前要验证这些,你必须:
1. 启动本地 LLM 或配外部 API
2. 等待每个 LLM 调用(往往数秒)
3. 处理偶尔超时/速率限制
4. 看不到稳定的「这个流程对吗」的确定性答案

**课程对标**:
执行层支持多种 Executor 实现:
- `RealExecutor`:真实调用(现状)
- `MockExecutor`:预置结果(新增)
- `AuditedExecutor`:真实调用 + 审计日志(新增)

**实现方向**:
```python
class MockTaskExecutor(TaskExecutor):
    """Mock 模式:不调 LLM,返回预置结果"""
    def __init__(self, fixtures: dict[str, TaskResult]):
        self.fixtures = fixtures
    
    def run(self, spec: TaskSpec, payload):
        if spec.name in self.fixtures:
            return self.fixtures[spec.name]
        raise ValueError(f"No mock fixture for {spec.name}")

class AuditedTaskExecutor:
    """审计包裹:记录每次任务调用,用于故障排查"""
    def __init__(self, real_executor: TaskExecutor):
        self.real = real_executor
    
    def run(self, spec: TaskSpec, payload):
        start = perf_counter()
        result = self.real.run(spec, payload)
        # 记录 spec.name, 耗时, result.ok, error 信息
        return result
```

flow 使用:
```python
# 生产:真实 LLM
flow = build_investment_document_review_flow(
    executor=TaskExecutor()
)

# 测试:mock 结果,确定性执行
mock_executor = MockTaskExecutor({
    "investment_document_extract": TaskResult(ok=True, result={"facts": [...]}),
    "investment_document_analyze": TaskResult(ok=True, result={"risks": [...]}),
    ...
})
test_flow = build_investment_document_review_flow(
    executor=mock_executor
)

# 审计:真实 + 日志
audited_executor = AuditedTaskExecutor(TaskExecutor())
flow = build_investment_document_review_flow(
    executor=audited_executor
)
```

**收益**:
- end-to-end flow 测试可在 < 100ms 内确定性跑完(vs 现在数十秒依赖真实 LLM)
- 流程逻辑验证和 LLM 质量验证分开,各自独立迭代
- 审计日志集中收集,便于生产故障排查

## 📌 关键决策点

### 不要做的事:模块二(意图分类→工具子集注入)

**为什么不适配**:
- 你的架构是确定性 LangGraph,不是 ReAct agent
- 模型不自由选工具,工具选择由图节点写死或 LLM router 决定
- 套用课程模块二只会加复杂度,没有实际收益

**你已有的「动态选择」**:
- `LearningEntryRouter`:学习入口路由(qa/summary/brief)
- `InvestmentDocumentReviewLLMRouter`:文档类型分类
- `route_after_review_framework`:chunk vs single_pass 选择

这些已经解决了「按场景灵活组合能力」的问题。

---

### LoopEngine/ToolRegistry 保留还是删除?

**建议:保留,但标注为预埋**

- 你现在不需要它们(图已写死)
- 但如果未来接入真实外部工具(行情数据源、PDF 抓取服务、市场数据 API),会需要一个通用的工具调度层
- LoopEngine 的 Protocol 设计(StepPlanner/Policy/Executor 分离)对「接入新工具类型」是有价值的

**做法**:
1. 在 `docs/3-1/` 写个"LoopEngine 何时启用"的说明文档
2. 在代码注释里标注:这是为「第 3-2 课 MCP 工具」预埋的基础
3. 暂不删除,但也暂不集成到现有 flow
