## 🎯 真正贴合你业务的四个工具管理改进

### 改进① 统一能力台账 — TaskSpec 补充治理元数据

**现状问题**:
- 9 个任务只有 name/prompt/models,无治理属性
- risk_assessment 会触发人工审批,但这个逻辑隐含在 flow 代码里,无法显式查询
- 没有按业务分类的标签(学习类 vs 文档审查类 vs 风险评估类)

**改造方向**:

```python
@dataclass(slots=True)
class TaskSpec:
    name: str
    prompt_name: str
    input_model: type[BaseModel]
    output_model: type[BaseModel]
    side_effect_level: str = "read"  # read / write / exec
    tag: str = ""                    # learning / document_review / risk
    desc: str = ""                   # 一句话描述
```

**元数据分配**:
- `side_effect_level="write"`: risk_assessment(触发审批)
- `side_effect_level="read"`: 其余 8 个(纯分析)
- `tag="learning"`: qa、summary、brief
- `tag="document_review"`: extract、analyze、synthesize、plan、single_pass
- `tag="risk"`: risk_assessment、reflection

**收益**:
- 风险审批、审计、灰度都能统一依赖这一个维度
- 为多租户/角色权限控制奠基
- **Phase 1 完成**

## 📊 为什么不做课程模块二、三?

### ❌ 不做"动态注入工具"(课程模块二)

**原因**:你的架构是 LangGraph 确定性管线,不是 ReAct agent。
- 工具选择已由图节点或 Router 决定
- 模型不自由选工具
- 套用动态注入只增加复杂度,没有收益

---

### ❌ 不做"Mock 执行器"

Mock 执行器是**测试基础设施**，不是工具管理。它解决的是"测试时不想调真实 LLM"的问题，应该归到独立的"测试策略"计划里。

---

### ⚠️ 暂不做"Plan Handler 抽象"——但它有真实价值，值得了解

**Plan Handler 解决什么问题？**

`generate_review_todo_plan` 现在长这样（`document_review_flow.py:1016`）：

```python
def generate_review_todo_plan(self, state):
    if should_use_chunk_review(state):
        todo_plan = self._build_chunk_review_todo_plan(state)  # 规则驱动
    else:
        result = self.executor.run(INVESTMENT_DOCUMENT_REVIEW_PLAN_TASK, ...)  # LLM 驱动
```

两条规划路径都有，逻辑也对。问题是**策略和流程耦合在一起**：想切换规划策略（测试时固定走规则、生产走 LLM、v2 版本只用 chunk review），唯一的办法是改 flow 代码。

Plan Handler 把这个 `if/else` 抽成一个注入点：

```python
class InvestmentDocumentReviewFlow:
    def __init__(self, ..., plan_handler=None):
        self.plan_handler = plan_handler or self._default_plan_handler()

    def generate_review_todo_plan(self, state):
        todo_plan = self.plan_handler.build_plan(state)  # 委托给注入的 handler
```

这样测试时传 `FixedAuditPlanHandler`，生产默认行为不变，v2 传 `ChunkRulePlanHandler`——不改 flow 代码。

**为什么当前计划先不做？**

| 场景 | 收益 |
|------|------|
| 测试时想固定规划策略、不调 LLM | ✅ 有收益 |
| 想灵活切换 v2/v3 规划逻辑 | ✅ 有收益 |
| 目前只有一套流程，跑得稳 | ❌ 现在改是过早抽象 |

现阶段本课的四个 Phase 专注于**工具元数据和治理**，Plan Handler 属于**流程编排层**。两者不冲突，但放在一起会让计划焦点分散。

**什么时候做合适？**

出现以下任一情况时再做：
- 测试 flow 逻辑时需要绕开 LLM（和 Mock 执行器一起做更自然）
- 开始开发 v2/v3 版本，需要切换规划策略
- 反思门（reflect_review_output）逻辑复杂到想单独测试

## 📌 关键决策点

### 保留 ToolRegistry/LoopEngine 还是删除?

**建议:保留,但明确标注为预埋**

- 你现在不需要它们(图已写死)
- 如果未来接入真实外部工具(MCP、API),会需要统一的工具调度层
- LoopEngine 的 Protocol 设计(StepExecutor 分离)对"接入新工具类型"是有价值的

**做法**:
1. 在 Phase 4 写个"LoopEngine何时启用"的说明文档
2. 在代码注释里标注:预埋基础,为第 3-2 课做准备
3. 暂不删除,等到真正需要时再启用
